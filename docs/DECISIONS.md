## Architecture / scope decisions

- **No separate gateway service.** BUILD_PLAN.md's demo scope simplifies to "2 Spring Boot apps + nginx". nginx in `deploy/nginx/nginx.conf` does path-based routing: `/api/ai/*` → ai-service, `/api/*` (else) → decision-service, everything else → the Angular static bundle with `try_files` fallback to `index.html` for client-side routing. This nginx config is reused as-is for the M6 production compose (CLAUDE.md says Caddy fronts nginx+services in prod; nginx's internal routing role doesn't change).
- **Maven multi-module layout.** Root `pom.xml` is a `pom`-packaged aggregator that imports `spring-boot-dependencies` and `spring-ai-bom` via `dependencyManagement` (rather than using `spring-boot-starter-parent` as the Maven parent), so the repo can have one custom root parent shared by both modules while still getting Spring Boot's managed dependency versions. A Maven wrapper (`mvnw`) is generated at the root for reproducible container builds that don't depend on a host-installed Maven.
- **Angular test runner.** Angular 22's `ng test` defaults to the new `@angular/build:unit-test` builder backed by Vitest + jsdom, not Karma/Chrome. Kept the default — it avoids needing a headless browser in CI/containers and is now the framework default.
- **`spring-boot-maven-plugin` needs an explicit `repackage` execution.** Because the root `pom.xml` imports `spring-boot-dependencies` via `dependencyManagement` instead of using `spring-boot-starter-parent` as the Maven parent, the default `repackage` execution that `starter-parent` normally wires in is not present. Without it the packaged jar has no `Main-Class` manifest entry (`no main manifest attribute, in app.jar` at container start). Fixed by declaring the `repackage` execution explicitly in the root `pluginManagement` for `spring-boot-maven-plugin`.
- **M1 scope kept minimal on purpose.** `decision-service` and `ai-service` ship only `spring-boot-starter-web` + `actuator` + a `/api/health` controller in M1. Flyway, the Postgres driver, kie-dmn-core, and Spring AI dependencies are added when M2/M5 actually use them, so each milestone's diff reflects only what that milestone needs.
- **`-parameters` compiler flag.** Same root cause as the `repackage` issue above: not inheriting `spring-boot-starter-parent` also means we lose its default `<parameters>true</parameters>` compiler config. Without it, Spring MVC can't resolve unannotated `@PathVariable`/`@RequestParam` names from reflection and every controller method fails with 400 `"Name for argument of type [java.lang.String] not specified..."`. Fixed by adding `<parameters>true</parameters>` to the root `pluginManagement` for `maven-compiler-plugin`. Caught by `DecisionServiceIntegrationTest` (every endpoint returned 400 before the fix).

## Decision engine and audit (M2)

- **No ORM.** `ModelVersionRepository`/`ExecutionRepository` use plain `JdbcTemplate` with hand-written SQL and `::jsonb`/`::int[]` casts bound as plain strings, rather than JPA/Hibernate. The audit schema's JSONB columns and the append-only/no-update nature of `decision_execution`/`decision_trace_step` don't benefit from an ORM, and records map more directly onto `RowMapper`s.
- **Trace capture via one listener instance per runtime + `ThreadLocal`.** `TraceCapturingListener` is registered once (never removed) on each compiled model's `DMNRuntime`. Per-evaluation state (the step buffer, sequence counter, decision-duration stack) lives in `ThreadLocal`s set by `begin()`/`end()` around each `evaluateAll` call. This is safe because DMN evaluation is synchronous on the calling thread — add/remove-per-request would have been unsafe, since concurrent requests would then share a mutated listener set mid-evaluation.
- **What's captured per CLAUDE.md rule 5 (not the fuller docs/Architecture.md wishlist).** Only `DECISION` and `DECISION_TABLE` trace steps are captured (decision name/result/inputs-in-scope, and matched rule rows via `AfterEvaluateDecisionTableEvent.getSelected()`, which is 1-indexed — matches the "row 3" style language a business user or the AI's citations would use). BKM and context-entry events are left as no-ops: none of the seed models use BKMs, so implementing and claiming test coverage for that path wasn't honest to do yet. Add it when a model actually needs it.
- **`matched_rules` stores `getSelected()`, not `getMatches()`.** `getSelected()` is the row(s) whose output actually won under the table's hit policy (for `FIRST`, exactly one even if several rows' conditions matched) — that's what "why did this decision come out this way" needs. `getMatches()` (all condition-matching rows before hit-policy resolution) isn't persisted.
- **Row hash chain ordering.** `ExecutionRepository.insert` chains `sha256(prevHash || canonical row)` using `ORDER BY executed_at DESC LIMIT 1` scoped by `model_key` to find the previous hash. For live traffic `executed_at` is `now()` and strictly increases with insertion order, so the chain is accurate. The seed generator backdates `executed_at` for demo realism (executions spread over the last 30 days) while actually inserting in a random order — so for seeded rows the chain reflects insertion order, not the displayed historical timestamp order. This only affects the demo's fabricated history, not real evaluations, and is noted here rather than solved with a stronger ordering column because the demo doesn't need tamper-evidence over fake history.
- **STRICT only, no row lock on the hash chain read.** Per BUILD_PLAN's demo scope ("Audit write: STRICT only"), the audit insert runs in the evaluation's own transaction/`@Transactional` method. The previous-hash lookup is a plain `SELECT`, not `SELECT ... FOR UPDATE`; under real concurrent writes to the same model this has a race (two evaluations could read the same `previousHash`). Acceptable for a demo's traffic levels; a production system would add locking or a sequence.
- **LISTEN/NOTIFY uses a dedicated `DriverManager` connection, not a pooled one.** `ModelPublishedNotifier` opens its own non-pooled JDBC connection (via `spring.datasource.url/username/password`, not the Hikari `DataSource` bean) because a `LISTEN` session must stay open for the process lifetime, which doesn't fit the pool's borrow/return model. Verified end-to-end in `DecisionServiceIntegrationTest`: a version is inserted directly (simulating what M3's publish endpoint will do), `pg_notify` is issued, and the test asserts the registry serves the new version within 15s with no restart. A benign `EOFException`/"model_published listener error, retrying" WARN is expected in logs at JVM/container shutdown — the listener's blocking read is torn down by the connection closing underneath it; it's cosmetic, not a functional issue.
- **`insurance-premium` and pgvector policy docs.** The seed loader creates `insurance-premium` (one published version, ~20 executions) alongside `loan-eligibility` (three versions, ~300 executions) per BUILD_PLAN's seed content spec. The "short policy document per model, embedded into pgvector" part of that spec is deferred to M5 — that's where ai-service's embedding model and pgvector access live; decision-service has no AI/embedding dependency.
- **Auth/roles are schema-only in M2.** `app_user` (seeded: `analyst`/`approver`/`auditor`, bcrypt password `demo`) exists and is seeded per BUILD_PLAN's M2 checklist, but no login/JWT endpoint reads it yet — `evaluate`/`simulate` take the caller identity from an `X-User` header (defaulting to `anonymous`) rather than an authenticated principal. Real auth enforcement (roles, author≠approver on approve) lands in M3/M4 where it's actually needed to gate an action.
- **`simulate` resolves only published versions for now.** docs/Architecture.md says simulate should run "against any version or draft". M2's `ModelRegistry` only compiles `PUBLISHED` rows, so simulating against an unpublished draft isn't wired yet — there's no draft-authoring flow to produce one until M3. `simulate` already works correctly for the real requirement M2 has test coverage for (dry-run against a published version, no audit write); draft support will be added alongside M3's test bench.

## Rule authoring lifecycle (M3)

- **DMN object model, not string/DOM editing.** `DmnXmlEditor` uses `kie-dmn-backend`'s real marshaller (`DMNMarshallerFactory.newDefaultMarshaller()` → `unmarshal`/`marshal` against `org.kie.dmn.model.api.Definitions`) to read and rewrite a decision table's rows. Everything the guided editor doesn't touch (item definitions, information requirements, other decisions) survives untouched because it's never serialized to text in between. Confirmed with `DmnXmlEditorTest`: reading a table into the guided-JSON DTO and writing it back unchanged reproduces identical evaluation outcomes, and editing one row changes exactly the outcome that row controls.
- **A "draft" is a `dmn_model_version` row, not a separate entity.** It progresses `status` in place (DRAFT → VALIDATED → TESTED → APPROVED → PUBLISHED) via `UPDATE`; only `PUBLISHED`/`RETIRED` rows are treated as immutable (CLAUDE.md rule 3). At most one row per `model_key` is ever "in progress" at a time (`findCurrentInProgress`) — editing again while a draft exists updates that same row rather than forking a second one; this matches the architecture's "a draft version is created from the latest published one" flow without needing a separate drafts table.
- **Lifecycle is strictly forward and auto-resets on edit.** Editing a draft always calls `updateDraftContent`, which also resets `status` back to `DRAFT` — so an edit after validation/testing requires re-validating and re-testing before it can be approved again. There's no support for "re-validate an already-TESTED row with no changes and keep TESTED"; the demo's flow is edit → validate → test → approve → publish in order, and that's the only path implemented.
- **Test run requires at least one saved test case to reach TESTED.** An empty test-case set can't be trivially "passed" — `runTests` only promotes to `TESTED` when `results` is non-empty and every case passes. Output comparison is lenient on numeric type (`BigDecimal` from the DMN engine vs. whatever a JSON body deserializes to) via a small recursive `lenientEquals`, and only checks the keys present in `expectedOutputs` (a test case can assert on one output and ignore the rest).
- **`DMNValidator.theseModels(Definitions...)` can't validate schema.** Calling `validateUsing(VALIDATE_SCHEMA, ...).theseModels(definitions)` against an already-parsed `Definitions` object fails every model with "Schema validation not supported for in memory object." Fixed by using the `Reader`-based `validator.validate(new StringReader(xml), Validation...)` overload instead, which validates the raw XML directly. Found by running `DmnValidationServiceTest` against the real engine, not assumed from docs.
- **`pg_notify(...)` must run as a query, not an update.** `JdbcTemplate.update(...)` calls `PreparedStatement.executeUpdate()`, which the Postgres driver rejects for any statement that returns a `ResultSet` — and `SELECT pg_notify(...)` does (one row). Fixed by calling it through `jdbcTemplate.queryForList(...)` in `ModelLifecycleService.notifyPublished`. Found the same way: real driver error ("A result was returned when none was expected"), not a guess.
- **Approval identity comes from the `X-User` header, not a request body field.** Consistent with `evaluate`/`simulate` from M2: the caller hitting the endpoint *is* the approver, so "must be a different user than the author" is enforced by comparing the header to `dmn_model_version.authored_by` — no separate `{"approver": "..."}` body needed.
- **Diff is rule-level, matched by `DecisionRule.id`.** `DmnDiffService` compares two versions' decisions by name; for decision tables it matches rows by their DMN `id` (preserved across edits by `DmnXmlEditor`) rather than by position, so reordering rows wouldn't falsely show every row as changed. For literal-expression decisions it compares the FEEL text directly. This is enough for the required "rows and expressions added/removed/changed" and for the AI's future `diffVersions` tool (M5) to cite specific rows — it does not attempt a token-level FEEL diff within a single rule.
- **Rollback republishes content, not history.** `rollback(modelKey, toVersion, actor)` creates a brand-new `dmn_model_version` row (next patch version, status `PUBLISHED` immediately — it skips the draft/validate/test/approve chain since the content already went through that once) copying the target version's exact XML and hash. The original target version row is untouched; `rule_change_audit` records the `ROLLBACK` action with `{rolledBackTo, newVersion}` so the audit trail shows it was a rollback, not a fresh edit.
- **Four-eyes and lifecycle-order violations are HTTP 409, not 400/403.** `ApproverMustDifferFromAuthorException` and `InvalidLifecycleTransitionException` (e.g. approving a non-`TESTED` draft, or editing a `PUBLISHED` version) both map to `409 Conflict` via `ApiExceptionHandler` — these are valid requests hitting an invalid *state* transition, which is what 409 is for, not malformed input (400) or an auth failure (403; there's no real auth yet per the M2 note above).

## Angular UI (M4)

- **No Angular Material / PrimeNG.** The architecture doc suggests "Angular Material (or PrimeNG for its richer data grid)", but pulling either in adds a version-compatibility unknown against Angular 22 (very recent at the time of writing) for a demo that doesn't need a rich data grid — the audit list and rule grid are simple tables. Hand-rolled a small CSS design system instead (`styles.scss`: CSS custom properties for color/spacing, `.card`/`.btn`/`.data-table`/`.status-pill` utility classes) shared across every feature page. Revisit if a future milestone needs something Material specifically provides (date pickers, virtualized grids).
- **Guided-table cells are plain text inputs, not typed FEEL pickers.** BUILD_PLAN's fuller vision (`docs/Architecture.md`) describes range/list/date pickers that emit valid FEEL per column type. Given the seed models' inputs are numbers and strings with simple unary-test FEEL (`>=700`, `[620..720)`, `"LOW"`), a plain text cell pre-filled with the current FEEL expression covers the real guided-editing need (BUILD_PLAN M4's own bullet: "typed cells, FEEL pickers, hit-policy dropdown, add/remove rows, inline validation errors") without inventing a FEEL-range-picker widget that only one or two column types would ever exercise. Validation errors surface from the real `DMNValidator` call, not client-side guessing.
- **Auth is a login screen in front of the `X-User` convention, not a JWT.** `POST /api/auth/login` validates the submitted password against the seeded `app_user` table's bcrypt hash and returns `{username, displayName, role}`; the Angular `AuthService` stores that in `localStorage` and a `userHeaderInterceptor` attaches it as `X-User` on every request — the exact header `evaluate`/`simulate`/the lifecycle endpoints have read since M2. There's no session token, so nothing stops a client from sending an arbitrary `X-User` value directly against the API (bypassing the login screen entirely). This matches the M2/M3 DECISIONS.md notes that real auth enforcement was deferred to "where it's actually needed" — a demo login gate was what M4 needed, not cryptographic session verification. A real deployment needs actual JWT/OIDC (the full architecture already specifies this).
- **Decisions-per-version and read-one-table are new backend endpoints, not hardcoded.** Rather than hardcode "loan-eligibility has decisions X, Y, Z" in the frontend, `GET /api/models/{key}/drafts/{id}/decisions` (list) and `.../decisions/{name}` (read one table) were added to `DmnXmlEditor`/`ModelsController` so the editor works for any model, including ones added later. Small, consistent with M3's existing XML-editing infrastructure.
- **Test bench trace capture required extending `AdHocEvaluator`.** `runTests`' evaluation (used to grade saved test cases against a draft) originally returned only an outputs map — no trace, since M3 didn't need one. M4's "test bench with trace highlighting" requirement needed it, so `AdHocEvaluator` now registers a `TraceCapturingListener` per ad-hoc runtime (safe: each ad-hoc runtime is throwaway/single-evaluation, unlike the shared registry runtimes in M2 which rely on the listener being request-scoped via `ThreadLocal`) and returns `AdHocEvaluationResult(outputs, status, trace)`. `TestCaseResultDto` gained a `trace` field; the same `app-trace-view` component used by the audit explorer renders it, so matched-row highlighting looks identical in both places.
- **UI verified with a real headless browser, not just curl/unit tests.** Angular component tests (Vitest/jsdom) check rendering logic in isolation, and curl checks the API — neither proves the actual pages work together end to end in a browser. Installed Playwright + Chromium in the sandbox and drove the full `docker compose` stack through the real M4 acceptance flow (login → edit → validate → test → approve as a different user → publish → audit search → execution detail), with screenshots at each step, resetting the Postgres volume between runs for a clean seeded state. This caught two real bugs before they'd have shipped: an Angular `@for` nested-loop index-aliasing mistake (`let colIndex = $index` needed per loop level, not a single shared `$index`) and a race in my own test script (not the app) where a second login's follow-up navigation fired before the login request resolved.

## AI service and chat (M5)

- **LLM provider: Anthropic, confirmed by the user, not defaulted.** This was flagged as genuinely the user's call going in (both in the kickoff brief and the M1 DECISIONS.md entry) and asked explicitly before starting M5, rather than picked silently. Wired concretely as `spring-ai-starter-model-anthropic` — see the next point for why not all three providers from the architecture doc.
- **Only Anthropic's starter is on the classpath, not all three.** The full architecture calls for `AI_PROVIDER=anthropic|openai|ollama` switching between starters. Including all three `spring-ai-starter-model-*` dependencies at once would auto-configure three separate `ChatModel` beans, which is a real bean-ambiguity risk I can't fully rule out without a key for each provider to test against. Since the user picked Anthropic specifically, `ai-service` only depends on `spring-ai-starter-model-anthropic`, wired through Spring AI's own `ChatClient`/`@Tool` abstractions (so the port itself stays provider-agnostic — swapping the starter dependency and the `ChatModel` autoconfiguration is still the only change needed to add another provider later). `AI_PROVIDER` is accepted in `.env.example` for forward-compatibility but not read yet.
- **Embeddings: local ONNX (`spring-ai-starter-model-transformers`), not Ollama.** The architecture doc suggests `embedding-provider: ollama` as a default; that needs a whole extra container in `docker-compose.yml`. `spring-ai-starter-model-transformers` runs the embedding model (all-MiniLM-L6-v2) in-process via ONNX Runtime, needs no API key and no extra service, at the cost of a one-time ~90MB model download on first start (cached after that). Simpler infra for a demo, same "no key needed for retrieval" property Ollama would have given.
- **Embedding model URL had to be pinned to Hugging Face Hub, not the library default.** `spring-ai-starter-model-transformers`'s default model URI is on `media.githubusercontent.com` (GitHub's git-lfs media CDN), which is blocked in this sandbox's egress policy. The fallback most people would reach for, `raw.githubusercontent.com`, is reachable but — because this specific file is git-lfs-tracked — serves the **lfs pointer** (a 133-byte text stub), not the ~90MB binary, which fails ONNX parsing with a confusing "protobuf parsing failed" error rather than a clear network error. Hugging Face Hub serves the identical published `all-MiniLM-L6-v2` ONNX export and is reachable, so `spring.ai.embedding.transformer.onnx.model-uri` is pinned there instead (see `ai-service/src/main/resources/application.yml`). This is sandbox-specific; a normal deployment VM would likely have reached the original URL fine, but pinning to a reachable, equally-authoritative source costs nothing and removes the dependency on an environment detail.
- **`ai-service` needs its own Flyway dependency and careful baseline config, not just `decision-service`'s.** Two real bugs here, both now fixed: (1) `ai-service`'s pom never actually had `flyway-core`/`flyway-database-postgresql` — `spring.flyway.enabled: true` in `application.yml` did nothing without the library on the classpath, so `ai_conversation` was never created and every conversation-related call failed. (2) Once added, Flyway refused to run at all ("non-empty schema but no schema history table") because `ai-service` shares the physical Postgres schema with `decision-service`'s already-migrated tables but uses its own history table name (`flyway_schema_history_ai`, per the M2 DECISIONS.md note on why they can't share one) — `baseline-on-migrate: true` is required for that split-ownership setup to work at all, and *additionally* `baseline-version: "0"` is required because baselining defaults to version "1", identical to this module's own `V1__ai_conversation.sql`, which makes Flyway treat V1 as already covered by the baseline and silently skip it forever.
- **Composite `estimateImpact` tool instead of a `simulate`-in-a-loop.** BUILD_PLAN's demo question 4 ("how many past cases would flip between 1.0.0 and 1.1.0") needs re-simulating many past executions against a different version. Doing that as the LLM calling `simulate` once per execution would blow past `max-tool-calls: 8` for anything but a tiny sample. Instead `estimateImpact(modelKey, fromVersion, toVersion, sampleSize)` does the whole sample-and-resimulate loop server-side in `RuleTools` (one tool call from the LLM's perspective) and returns a summary (`sampled`, `flipped`, up to 5 `examples`). `queryExecutions` also gained a `version` filter (decision-service's search already supported it; the tool just didn't expose it) so `estimateImpact` can pull exactly the executions that ran on `fromVersion`.
- **Tool-call transparency via `ToolContext`, not `ThreadLocal`.** M2's DMN trace capture uses a `ThreadLocal` because DMN evaluation is fully synchronous on the calling thread. Spring AI's streaming tool-execution loop gives no such guarantee (reactive execution can hop threads), so a `ThreadLocal`-based "which tools ran" log would silently lose entries. Instead every `@Tool` method takes a trailing `ToolContext` parameter (excluded from the JSON schema the LLM sees — confirmed via `ToolCallback.call(String, ToolContext)` in the real `spring-ai-model` jar before relying on it) and appends to a `CopyOnWriteArrayList` passed in via `.toolContext(Map.of(..., ToolCallLog.CONTEXT_KEY, toolLog))`, which is a plain shared mutable reference regardless of which thread eventually calls the tool.
- **SSE via plain `Flux<String>` on Spring MVC, not WebFlux.** `ChatClient.stream().content()` returns `Flux<String>`; returning it from an `@PostMapping(produces = TEXT_EVENT_STREAM_VALUE)` method works directly on `spring-boot-starter-web` (Spring MVC's reactive-return-type support), with no need to pull in a second, fully reactive web stack just for this one endpoint.
- **Frontend consumes SSE via `fetch()` + a manual line parser, not `EventSource`.** The browser's native `EventSource` only supports `GET` with no custom headers or body, but sending a message needs both a JSON body and the `X-User` header. `ChatApiService.streamMessage` uses `fetch()` and reads `response.body` as a stream, splitting on `\n` and stripping the SSE `data:` prefix itself.
- **Markdown rendering: `marked` + Angular's `DomSanitizer`, not a hand-rolled renderer.** BUILD_PLAN calls for "streaming markdown" in the chat UI. Added the small, well-known `marked` package rather than writing a partial markdown-to-HTML converter; output is sanitized through Angular's `DomSanitizer` before binding via `[innerHTML]` since it's LLM-generated text, not content the user wrote — not fully trusted, even though it isn't raw user HTML either. The component needs `ViewEncapsulation.None` because Angular's emulated style encapsulation can't scope CSS onto content set via `[innerHTML]` (it never passes through Angular's template compiler).
- **"Describe a rule" creates a draft; there's no separate accept/reject-diff UI.** BUILD_PLAN's fuller description imagines the AI's proposed rows shown as a diff the user explicitly accepts or rejects row by row. `proposeChange` already only ever creates/updates a DRAFT (CLAUDE.md rule 6) — never publishes — so reloading the rule editor after the AI responds shows the result as an ordinary draft the analyst reviews in the *same* guided-table editor and diff/validate/test/approve/publish flow every other edit goes through (M3/M4), rather than a second, parallel review UI. This is a smaller surface than a dedicated accept/reject-per-row control, traded for not duplicating the review mechanism BUILD_PLAN already specifies elsewhere.
- **Citations are plain text, not clickable links.** BUILD_PLAN's chat UI bullet calls for "clickable citations that open the exact table row or trace step." The system prompt instructs the model to cite model version / decision name / row number / execution ID inline (CLAUDE.md rule 7), and it does — but turning a citation substring in free-form LLM text into a router link reliably needs structured citation markers from the model (e.g. a custom syntax the prompt asks for and the frontend parses), which wasn't built this milestone. Scope trim, not a correctness issue: every claim is still cited in the visible text, just not hyperlinked.
- **No token-count logging yet.** `ai_interaction_audit.token_count` exists in the schema (M2) but `ChatService` always writes `null` for it. Spring AI's streamed `Flux<String>` content doesn't carry usage metadata the way `Flux<ChatResponse>` would on its final element; wiring that up was left out rather than logging an invented estimate (e.g. `text.length()/4`) as if it were real.
- **`ChatEndToEndTest` is gated, not run by me.** It drives the actual five BUILD_PLAN demo questions through a real decision-service container and the real Anthropic API, asserting on response content. This sandbox has no `ANTHROPIC_API_KEY` (the user supplies their own, per the question asked at the start of this milestone), so the test is annotated `@EnabledIfEnvironmentVariable(named = "ANTHROPIC_API_KEY", matches = ".+")` and was *not* exercised — everything reachable without a real key (all tools against real seeded data, real local embeddings/retrieval, the full conversation/persistence plumbing) was. Run it directly once a key is available: `ANTHROPIC_API_KEY=sk-... ./mvnw -pl ai-service test -Dtest=ChatEndToEndTest`.
